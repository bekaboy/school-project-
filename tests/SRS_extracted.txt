1. Introduction
The introduction to the Software Requirement Specification (SRS) document provides an overview of the complete specification. This document contains all the information needed by a software engineer to adequately design and implement the pharmaceutical wholesale inventory and sales management software product described by the requirements listed herein.
1.1 Purpose
The purpose of this SRS document is to define the functional and non-functional requirements for the Pharmaceutical Wholesale Inventory and Sales Management System intended for Era Med Pharmaceutical Wholesale PLC. The document serves as a contractual basis between the development team and stakeholders, providing a detailed specification that will guide design, implementation, testing, and validation activities. The intended audience includes software developers, project managers, quality assurance testers, and business stakeholders who will review and approve the system requirements.
1.2 Scope
This Software Requirements Specification covers the development of a computerized Inventory and Sales Management System for Era Med Pharmaceutical Wholesale PLC, a pharmaceutical wholesaler operating in Addis Ababa, Ethiopia.
What the system will do:
The system will replace the company's current manual and semi-digital processes with an integrated digital platform. The system will:
- Manage pharmaceutical product information including batch numbers, expiry dates, and stock quantities
- Track inventory movements in real-time using FIFO (First In First Out) deduction logic
- Alert users about products approaching expiry (within 90 days) and low stock levels
- Support the complete sales workflow from order creation to delivery confirmation
- Enable sales representatives to view real-time stock availability
- Provide payment verification capabilities with proof documentation
- Coordinate delivery operations with status tracking
- Generate automated reports including sales performance, inventory levels, and financial summaries
- Provide a management dashboard with key performance indicators
- Maintain a complete audit trail of all critical operations
- Implement role-based access control with five distinct user roles
- Support both Amharic and English languages with user-toggle functionality
- Operate as a web-based application accessible from computers and mobile devices
What the system will not do (Out of Scope):
- Replace the company's existing communication methods (phone, WhatsApp, Telegram) - though it will reduce dependency on them for operational coordination
- Integrate with external banking systems for automatic payment verification
- Provide customer-facing online ordering capabilities
- Support multiple branch locations or centralized multi-warehouse operations
- Include supplier management or purchase order generation from suppliers
- Provide advanced accounting features beyond basic receipt generation
- Offer native mobile applications (only responsive web design)
- Implement SMS or email notification systems
- Support barcode scanning hardware integration
- Include real-time GPS tracking for delivery vehicles
- Perform predictive analytics or AI-based demand forecasting
- Manage employee payroll or HR functions
The system scope is limited to Era Med Pharmaceutical Wholesale PLC's single-location operations and will serve approximately 8 users managing 20-30 pharmaceutical products with multiple batch variations. The system is designed as a standalone web application with no planned integration with external enterprise systems beyond basic database operations.
1.3 Overview
This SRS document is organized according to the IEEE SRS template standard. Section 2 provides a general description of the product from a high-level perspective. Section 3 contains detailed specific requirements organized by category including external interfaces, functional requirements, use cases, non-functional requirements, design constraints, and database requirements. Section 4 describes the change management process that will be used to modify requirements throughout the project lifecycle. Appendices provide supporting diagrams and detailed specifications.




2. General Description
This section describes general factors that affect the product and its requirements without stating specific requirements. It provides context to make the detailed requirements easier to understand.
2.1 Product Perspective
The Pharmaceutical Wholesale Inventory and Sales Management System is a standalone web application that will operate as a comprehensive business management solution for pharmaceutical wholesale operations. The system will integrate multiple functional areas including inventory management, sales order processing, payment verification, delivery management, and reporting into a unified platform.
The system consists of:
- A frontend web interface accessible via standard web browsers
- A PostgreSQL database hosted on Supabase cloud platform
- Authentication and authorization services provided by Supabase Auth
- Server-side APIs for data operations and business logic
- Storage services for payment proofs and product images
The system does not directly interface with external pharmaceutical systems but may later integrate with accounting software or banking APIs as future enhancements.
2.2 Product Functions
The system provides the following high-level functions:
User Management and Authentication:
- Secure login and logout functionality
- Role-based access control with five distinct roles
- Password reset capability
- Session management with automatic timeout
Product and Batch Management:
- Create, read, update, and delete product records with comprehensive pharmaceutical information
- Manage batch/lot numbers with expiry dates and manufacturing dates
- Track product images and storage requirements
- Maintain product category and manufacturer information
Inventory Management:
- Real-time stock level tracking across all products and batches
- Automatic stock deduction using FIFO (First In First Out) method
- Stock adjustment functionality for damaged, expired, returned, or corrected inventory
- Expiry alerts for products expiring within 90 days
- Minimum stock level alerts based on reorder quantities
- Comprehensive inventory audit trail
Sales Management:
- Create and manage customer sales orders with multiple line items
- Real-time stock availability validation during order entry
- Generate proforma invoices for customer review
- Automatic invoice generation after payment verification
- Order status tracking through complete workflow
- Customer relationship management with contact information
Payment Verification:
- Upload payment proof documentation (images or PDFs)
- Verify or reject customer payments with detailed notes
- Generate numbered receipts for verified payments
- View payment history and status reports
- Block delivery preparation for unpaid orders
Delivery Management:
- Assign orders to delivery drivers
- Driver interface for viewing assigned deliveries
- Delivery status updates (delivered, failed, rescheduled)
- Capture delivery confirmation details including signatures
- Delivery performance tracking and reporting
Reporting and Dashboard:
- Real-time dashboard with 10+ KPI widgets
- Interactive charts showing sales trends, product distribution, and payment methods
- Weekly automated reports generated and emailed to management
- Comprehensive report library with date range filtering
- Export capabilities to PDF and Excel formats
System Administration:
- User account creation and management
- Audit logging of all critical system actions
- System configuration and settings management
- Data import/export functionality
2.3 User Characteristics
The system will be used by five distinct user roles with varying technical proficiencies:
Sales Representatives:
- Moderate computer literacy
- Familiar with pharmaceutical products and customers
- Primary goal: efficiently create orders and serve customers
- Will benefit from intuitive, fast order entry interface
Store Managers:
- High computer literacy or willingness to learn
- Responsible for inventory accuracy and control
- Need detailed inventory views and adjustment capabilities
- Require clear visibility into stock levels, expiry dates, and alerts
Finance Officers:
- Moderate to high computer literacy
- Focus on payment verification and receipt generation
- Need secure document upload and verification workflow
- Require clear audit trails for financial compliance
Delivery Drivers:
- Possibly lower computer literacy
- Need simple, mobile-friendly interface
- Primary goal: view assigned deliveries and update status quickly
- May use smartphones or tablets in the field
- Require minimal training and intuitive control
Technical Managers/Owners:
- Advanced technical understanding
- Need comprehensive access to all system features
- Require detailed reporting and analytics capabilities
- Responsible for user management and system configuration
- Will use dashboard for strategic decision-making
All users will have basic web browser experience. The system will be designed with usability as a priority, particularly for delivery drivers who may have limited technical background. The bilingual interface (Amharic and English) accommodates users with different language preferences.
2.4 General Constraints
The following constraints affect system design and implementation:
Technology Constraints:
- Must use Supabase as the backend platform with PostgreSQL database
- Must implement Row Level Security (RLS) for data protection
- Frontend must be a web application compatible with modern browsers
- PDF generation capability required for invoices and reports
- Real-time updates optional but desirable
Performance Constraints:
- System must support up to 10 concurrent users
- Page load time must not exceed 3 seconds
- Transaction processing must complete within 2 seconds
- Report generation must complete within 5 seconds
Security Constraints:
- All data transmission must use HTTPS encryption
- Session timeout after 30 minutes of inactivity
- Role-based access control enforced at database level
- Audit logging required for all critical operations
- Password policies requiring strong passwords
Data Constraints:
- Database size limited by Supabase free tier (500 MB initial)
- Storage limited to 10 GB on free tier
- Designed for small-scale operation: 30 products, 100 customers, 15 orders per day
- Must handle product images and payment proof documents
Timeline Constraints:
- Project duration limited to 8 weeks (2 months)
- Development must follow iterative sprint approach
- User training and documentation required within timeline
- Must allow time for user acceptance testing
Resource Constraints:
- Minimal budget requiring use of free tier services
- Single branch deployment only (no multi-branch support initially)
- No dedicated hardware purchases planned
- Development by student team with learning curve for technologies
Regulatory Constraints:
- Must comply with pharmaceutical record-keeping requirements
- Audit trails required for all inventory and financial transactions
- Data retention policies must preserve all records indefinitely
- Must support professional invoice formats with company stamp areas

REQ-INV-009: The system SHALL NOT include temperature monitoring for storage conditions.
REQ-INV-010: The system SHALL NOT include multi-branch or multi-warehouse support.
REQ-INV-011: The system SHALL NOT include advanced accounting features (general ledger, accounts payable/receivable).
REQ-INV-012: The system SHALL NOT include employee payroll or HR management.
REQ-INV-013: The system SHALL NOT include predictive analytics or AI-based forecasting.
REQ-INV-014: The system SHALL NOT support offline mode; continuous internet connectivity is required.
REQ-INV-015: The system SHALL NOT include automated data migration from existing Excel files (manual data entry is acceptable).
REQ-INV-016: The system SHALL NOT include credit card processing or integration with payment gateways.
REQ-INV-017: The system SHALL NOT include a document management system beyond payment proof uploads.
REQ-INV-018: The system SHALL NOT include chat or messaging functionality between users.
 	3.6 Design Constraints
REQ-DES-001: The system SHALL be implemented as a web application accessible via browser, not a desktop application.
REQ-DES-002: The frontend SHALL be implemented using React framework or vanilla HTML/CSS/JavaScript (team decision).
REQ-DES-003: The backend SHALL use Supabase (PostgreSQL) as the database and authentication platform.
REQ-DES-004: The system SHALL use Row Level Security (RLS) in Supabase for data access control.
REQ-DES-005: The system SHALL be hosted on free-tier services (Supabase, Vercel/Netlify) with no monthly cost.
REQ-DES-006: All code SHALL be maintained in a Git repository (GitHub) with version control.
REQ-DES-007: The system SHALL be developed using a 2-month timeline (8 weeks) from project start.
REQ-DES-008: The system SHALL be designed for a single branch/warehouse location only.
REQ-DES-009: The system SHALL use English for data entry (product names, customer names) and support Amharic for UI text.
REQ-DES-010: The system SHALL NOT require any paid software licenses; all tools SHALL be open-source or have free tiers.
                           








 3.7 Logical Database Requirements

User email addresses
Product ID
Batch numbers per product
Invoice numbers
Proforma invoice numbers

REQ-DB-005: The database SHALL maintain transaction integrity for operations that affect multiple tables (e.g., order creation with items, stock deduction with invoice generation).

4. Change Management Process
This section defines the process for managing changes to the Software Requirements Specification (SRS) throughout the project lifecycle. All changes must be controlled to ensure that the requirements remain accurate, consistent, and traceable.
4.1 Change Request Submission
Any stakeholder (project team member, client, advisor) may submit a change request. Change requests shall be documented using the Change Request Form (see Appendix A) and submitted to the project manager via email or issue tracking system (GitHub Issues).
Each change request shall contain:

Unique identifier (CR-XXX)
Date of submission
Submitter name and role
Description of the change (including rationale)
Priority (Low, Medium, High, Critical)
Impact assessment (if known)






4.2 Change Review and Approval
The project manager, together with the technical lead, shall review all change requests weekly. The review committee shall evaluate each request based on

Approved changes shall be categorized as:
Minor Change: No significant impact on scope, schedule, or architecture. May be implemented immediately.
Major Change: Affects project scope, schedule, or architecture. Requires formal approval from the client and academic advisor.
4.3 Change Documentation and Traceability
Upon approval, the change shall be documented in the Change Log (see Appendix B) and the SRS shall be updated accordingly. All changes shall be versioned, and the SRS version number shall be incremented according to semantic versioning:
Major version increment (X.0): Significant changes to scope or architecture
Minor version increment (x.Y): New requirements added or existing requirements modified
Patch version increment (x.y.Z): Corrective changes (typos, clarifications)
